# Packaging + Self-Update for QuickInterviewEditor

**Date:** 2026-08-17
**Status:** Draft (awaiting review)
**Author:** Brian Keane (with Claude + Codex adversarial architecture review)

## Goal

Ship QuickInterviewEditor to a handful of users as a download from Brian's own
website, and let each user self-update to a new version with one click. Updating
must **preserve the user's saved API key** (stored in the login Keychain).

## Non-goals

- Mac App Store distribution (this is Developer ID / outside-the-store).
- Delta/differential updates (a trap at this user count; see Decision 2).
- Full CI-driven release in v1 (the heavy engine freeze makes hosted CI
  impractical; see Decision 3 and "Later: CI split").
- Auto-update of the frozen Python engine independent of the app (the engine
  ships inside the `.app`; a new engine = a new app version).

## Background (verified in-repo)

- App is generated by **XcodeGen** from `QuickInterviewEditor/project.yml`.
  Bundle id `fm.playola.QuickInterviewEditor`, Team ID `FSRSPV9N9Q`,
  deployment target **macOS 15.0**.
- The app embeds a **PyInstaller one-folder freeze** of a torch/whisperx engine
  plus a second cut-suggester engine at `Contents/Resources/engine/`. The freeze
  is **Apple-Silicon-only, multi-GB, and slow**. Full app is ~1-4 GB.
- Existing `packaging/` scripts already do build → sign → notarize:
  - `build-app.sh` — `xcodebuild` Release **unsigned**, then `ditto`-embeds the
    two frozen engine folders into `Contents/Resources/engine/`.
  - `sign-app.sh` — Developer ID signature + hardened runtime.
  - `notarize-app.sh` — `xcrun notarytool submit --wait` + `stapler staple`;
    accepts a `NOTARY_PROFILE` login-Keychain profile **or** an ASC API key.
  - `app.entitlements` / `engine.entitlements`.
- The API key lives in the **login Keychain** as a generic-password item under a
  stable, machine-wide service string
  (`fm.playola.QuickInterviewEditor.anthropicAPIKey`, account `anthropic`) — see
  `Core/KeychainClient.swift`. It is **not** derived from the bundle path, and is
  **not** in UserDefaults/plist.
- `fastlane/` exists (mac platform) with `test` / `lint_code` / `format_check`
  lanes only. GitHub Actions (`.github/workflows/tests.yml`) runs tests only.
- Sibling app `playola-radio-ios` manages signing secrets with **fastlane match**
  (private git repo `fastlane-match-certs-and-profiles`, unlocked by
  `MATCH_PASSWORD`) + an ASC API key env var. `match` is Apple-cert-specific and
  cannot hold a Sparkle EdDSA key (see Decision 1).

## Components

### 1. Sparkle integration (in the app)

- Add **Sparkle 2.x** as an SPM dependency in `project.yml` (pin an exact
  version tag; commit `Package.resolved`).
- `Info.plist` (via `project.yml` settings):
  - `SUFeedURL` = `https://<bucket-host>/qie/appcast.xml` (HTTPS only).
  - `SUPublicEDKey` = the EdDSA **public** key (safe to ship; base64).
  - `SUEnableAutomaticChecks` = `true` (Sparkle shows first-run consent prompt).
  - `SUScheduledCheckInterval` (e.g. daily).
- A **"Check for Updates…"** menu item wired to Sparkle's standard user-driven
  updater. Per the app's MV rules, the controller is created in the app entry /
  a thin `UpdaterClient` dependency; **no update logic in views**. The menu
  action calls the model; the model calls the client.
  - `UpdaterClient` (`Core/UpdaterClient.swift`): a `Sendable` dependency struct
    (`checkForUpdates: @Sendable () -> Void`, plus `canCheckForUpdates`
    observable state) with a `liveValue` backed by Sparkle's `SPUStandardUpdaterController`
    and a `testValue` no-op. Keeps Sparkle out of the view and out of tests.
- **Hardened runtime / entitlements:** keep
  `com.apple.security.cs.disable-library-validation` (torch loads unsigned native
  libs; without it the frozen engine won't launch under HR). Do **not** add
  `get-task-allow` to release entitlements. App is **not** sandboxed, so we do
  **not** add Sparkle's sandbox-only XPC entitlements.

### 2. Packaging: one notarized DMG for both paths

- Single **notarized + stapled DMG** is both the website download and the
  Sparkle enclosure. No separate zip.
- Add `packaging/make-dmg.sh` wrapping `create-dmg` (Homebrew) to produce
  `QuickInterviewEditor-<version>.dmg` from the signed/notarized `.app`, then
  staple the DMG itself.
- Signing is **inside-out**: every nested `.dylib`, framework, helper, and Python
  binary under `Contents/Resources/engine/` is signed before the outer app.
  `--deep` is used **only** as a verification smoke test, never as the signing
  strategy. (Confirm `sign-app.sh` already signs inside-out; if it relies on
  `--deep` to sign, fix it as part of this work.)
- Verification gate in the release lane:
  ```sh
  codesign --verify --deep --strict --verbose=4 QuickInterviewEditor.app
  spctl --assess --type execute --verbose=4 QuickInterviewEditor.app
  xcrun stapler validate QuickInterviewEditor-<version>.dmg
  ```

### 3. Appcast generation

- `packaging/appcast.rb` (or a small script) that **idempotently** appends a new
  `<item>` to `appcast.xml` for the current version. Fields:
  - `sparkle:version` = `CFBundleVersion` — a **monotonically increasing
    integer**, never a git SHA.
  - `sparkle:shortVersionString` = `CFBundleShortVersionString` (display).
  - `sparkle:minimumSystemVersion` = `15.0`.
  - `<enclosure url=… length=… type="application/octet-stream"
    sparkle:edSignature=…>` — length is the DMG byte size; edSignature from
    `sign_update`.
  - `<pubDate>`, `<title>`, and a `<description>` (release notes; can be inline
    CDATA or a hosted HTML URL).
- The script reads the just-built DMG + `sign_update` output; it never invents
  metadata. A bad appcast = a broken update channel for everyone, so it is
  validated (XML well-formed + required fields present) before upload.

### 4. Release pipeline — `fastlane mac release`

New lane in `QuickInterviewEditor/fastlane/Fastfile`. Steps:

1. `ensure_git_status_clean`; refuse to release from a dirty tree.
2. **Version bump** (single source of truth). Marketing version +
   `CFBundleVersion` integer live in `project.yml`; the lane bumps them, then
   re-runs XcodeGen so the Xcode project picks them up. (See Decision 4.)
3. **Engines:** if a cached freeze exists and Python deps are unchanged, reuse
   `packaging/dist/logic-markers-engine` + `cut-suggester-engine`; else run
   `package-engine.sh` + `package-cut-suggester.sh`. (Freshness check: hash
   `requirements.txt` + the spec files; store the hash beside the freeze.)
4. `packaging/build-app.sh`
5. `packaging/sign-app.sh`
6. `packaging/notarize-app.sh` + staple
7. `packaging/make-dmg.sh` (+ staple DMG)
8. Sparkle `sign_update <dmg>` → EdDSA signature (key from login Keychain,
   Decision 1)
9. `packaging/appcast.rb` → append + validate
10. `aws s3 cp` DMG + `appcast.xml` to the bucket (old DMGs retained). Uses the
    existing AWS creds/profile already used for the downloads bucket.
11. Print the release-verification checklist (Testing section) — the human runs
    the Sparkle round-trip test before announcing.

CI (`tests.yml`) additionally gains a cheap **validation** job: XcodeGen builds,
tests/lint pass, `appcast.xml` parses, and `project.yml` version fields are
well-formed integers/semver. CI does **not** build the DMG.

## Data flow: the "preserve the API key" guarantee

- Keychain access is governed by the app's **code-signing designated
  requirement (DR)**, not the bundle path.
- Sparkle replaces the `.app` **in place**, keeping the same Team ID + bundle id +
  Developer ID signing identity → the new build satisfies the old DR → the
  existing generic-password item is read **silently**, no prompt.
- **The one real catch (Codex):** a key saved while running a *dev/ad-hoc-signed*
  build has a different DR, so a Developer ID build cannot read it silently. In
  practice users only ever run Developer ID builds, so this is a non-issue — but
  we prove it every release (Testing).
- **Invariants that must never change** (documented in `packaging/README.md` and
  a comment in `KeychainClient.swift`):
  - Team ID `FSRSPV9N9Q`
  - bundle id `fm.playola.QuickInterviewEditor`
  - Keychain service `fm.playola.QuickInterviewEditor.anthropicAPIKey`, account
    `anthropic`, and **no** `kSecAttrAccessGroup` / sandbox / synchronizable
    change.

## Error handling & failure modes (from Codex adversarial review)

| Failure | Mitigation |
|---|---|
| Key unreadable after update | Same DR across versions; release test proves silent read; invariants documented. |
| Multi-GB enclosure looks "hung" | Full updates only; Sparkle progress UI; keep DMG on fast S3/HTTPS; consider CloudFront later if bandwidth bites. |
| Enclosure download fails halfway | Sparkle re-downloads on next check; old version keeps working; old DMGs retained for manual recovery. |
| App translocation ("app is damaged"/random path) | First-launch check: if running from a read-only volume or outside `/Applications`, offer to move (LetsMove-style). Engine paths resolve from `Bundle.main.resourceURL`, never cwd; never write into `Contents/Resources/engine/`. Sparkle installs into the existing app location, avoiding translocation on updates. |
| Nested engine binary unsigned → notarization/HR failure | Sign inside-out; verify with `codesign --verify --deep --strict` + `spctl`. |
| Lost EdDSA private key | **No installed app can verify future updates** → users must re-download manually. Key backed up offline (encrypted); rotation path = ship a version trusting the new public key before signing with the new private key. |
| Bad appcast metadata | `appcast.rb` validates before upload; CI validates the committed appcast. |
| Release from dirty/unreviewed tree | `ensure_git_status_clean` + release only from the release branch. |

## Testing

**Automated (CI + local `fastlane test`):**
- `UpdaterClient` model interactions tested against the `testValue` no-op (menu
  action → client called; `canCheckForUpdates` state). Swift Testing, per repo
  conventions; Sparkle never runs in tests.
- Appcast validation unit: given a DMG + signature, the generated `<item>` has
  required fields, integer `sparkle:version`, and parses as XML.

**Manual release-verification checklist (run every release, printed by the lane):**
1. `spctl --assess --type execute` and `stapler validate` pass on a freshly
   downloaded DMG (download from the S3 URL, not the local build).
2. On a clean Mac / clean user account: mount DMG, drag to `/Applications`,
   launch — no Gatekeeper block, no translocation, engine runs.
3. **Keychain round-trip:** install vN (Developer ID) from DMG, save an API key,
   run a cut-suggestion to confirm it works. Publish vN+1. In the installed vN,
   "Check for Updates…" → install → relaunch → confirm the API key still works
   **with no Keychain prompt**.
4. `codesign -d -r-` DRs of vN and vN+1 match on the invariants above.

## Decisions

### Decision 1 — Sparkle EdDSA key custody
**Chosen:** store the EdDSA **private** key in the **login Keychain** (Sparkle's
`generate_keys` default; `sign_update` reads it automatically). Public key ships
in `Info.plist` as `SUPublicEDKey`. An **encrypted offline backup** of the
private key is kept (losing it breaks the update channel forever).
**Why:** mirrors QIE's existing `qie-notary` notarytool-profile-in-Keychain
approach and Sparkle's native flow; keeps the secret out of git.
**Divergence from playola-radio-ios:** the iOS app uses fastlane `match` (private
git certs repo), but `match` is Apple-cert-specific and cannot hold an EdDSA key,
so the "same principle" (secret outside git, supplied at release) is preserved
via the Keychain instead. **Revisit** when the CI split lands (then move to a
private repo / CI secret, like match's `MATCH_PASSWORD`).

### Decision 2 — Full updates, no deltas
Delta updates are fragile when PyInstaller output changes wholesale between
builds and add release complexity for no benefit at this user count. Ship full
DMGs.

### Decision 3 — Local release in v1
Repeated multi-GB Apple-Silicon PyInstaller freezes on GitHub-hosted runners are
slow and flaky. v1 release runs locally on Brian's Mac. CI keeps
tests/lint/validation. (User approved.)

### Decision 4 — Single version source of truth
Marketing version + `CFBundleVersion` integer live in `project.yml`; the release
lane bumps them and re-runs XcodeGen. `sparkle:version` == `CFBundleVersion`.

## Later: CI split (documented, not built in v1)

Decouple the heavy freeze from every release:
- Freeze the engines **rarely** into a **versioned S3 artifact** (keyed by the
  requirements/spec hash).
- The app-release job (CI or a **self-hosted arm64 Mac runner**) pulls that
  artifact and only builds/signs/packages the app — that part is CI-able.
- Move the EdDSA key + AWS creds to CI secrets at that point.

## Resolved review questions

1. **S3 bucket + public HTTPS host for `SUFeedURL`.** Brian supplies/configures
   these manually. The release lane and `Info.plist` read them as config, not
   hardcoded literals:
   - `RELEASE_S3_BUCKET` + `RELEASE_S3_PREFIX` (e.g. `qie/`) — the `aws s3 cp`
     target.
   - `SUFeedURL` = the public HTTPS URL for `<prefix>/appcast.xml` (raw bucket
     URL or a CloudFront domain — Brian's choice, set once in `project.yml`).
2. **`sign-app.sh` inside-out signing.** Fixing it is **in scope** — verify it
   signs nested engine binaries inside-out and does not rely on `--deep` to sign.
3. **AWS credentials for upload.** Use `AWS_PROFILE` (default `default` — the
   single configured profile on the release machine), overridable via env. No new
   credential machinery in v1; the CI split later moves this to a CI secret.
   Verify the `default` profile can write to the bucket during implementation.
4. **Release notes.** **Inline** in the appcast (`<description>` CDATA). No hosted
   HTML page.
